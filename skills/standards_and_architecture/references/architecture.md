# Architecture and layout reference

Technical contracts are defined in [the standards skill](../SKILL.md).

## Data Storage Layout

Paths have three roots, which may be different directories:

| Root | Contents |
|---|---|
| `REPO_PATH` | Source code and `config/` prompts/settings. |
| `LOCAL_STORAGE_PATH` | Application data under `storage/`, including source datasets and insights. |
| `LOCAL_DATA_PATH` | Machine-local `docling_data/` and disposable `cache/`. |

Domain paths come from `<REPO_PATH>/config/storage_domains.json`.
Use the shared dataset-path APIs.
Optional application-storage mirroring (such as rclone/Google Drive) runs
outside skills. Existing Dealum and website imports are source acquisition,
not storage mirroring; their side effects belong in their workflow documentation.

Under **`REPO_PATH`**:

*   `config/` — Prompts and settings in `.md` and `.json` files. The configuration module compiles these into a runtime tree cached under `LOCAL_DATA_PATH/cache/`.

Under **`LOCAL_STORAGE_PATH`**:

*   `storage/startups/<dataset_name>/datasets/` — raw startup data rooms.
    *   `__active_dataset__.md` — A readable marker file. If present, it signals to batch jobs (like `bulk_refresh`) that this startup should be actively processed.
*   `storage/startups/<dataset_name>/insights/` — generated startup AI reports and profiles.
*   `storage/community/<dataset_name>/datasets/` — primary community/member datasets.
*   `storage/community/<dataset_name>/insights/` — generated community AI reports and profiles.
*   `storage/generated/<dataset_name>/datasets/` — datasets assembled from insights through `dataset_from_insight`; indexing is separate. Ranking reads stored profiles directly.
*   `storage/generated/<dataset_name>/insights/` — insights associated with generated datasets, when applicable.
*   `storage/<domain>/<dataset_name>/insights/persons-in-dataset-<dataset_name>-manual.md` — manually maintained person lists generated by `persons_in_dataset`. Once created, these files are treated as user-edited source-of-truth inputs and are never overwritten.

Under **`LOCAL_DATA_PATH`**:

*   `docling_data/datasets2md/<domain>/<dataset_name>/datasets/` — durable machine-local parsed Markdown. It is not disposable cache and is outside the synchronized application-storage tree.
*   `cache/` — disposable runtime cache and temporary operational state.

## Architecture

Two top-level Python packages: `skills/` (documented workflows, operational tools
and established shared utilities) and `lib/` (shared infrastructure and domains).
Instruction-only skills have no executable entry point.

### Architectural Layers

`lib/` is no longer a flat utility folder. It is organized around storage,
dataset ingestion, insight lifecycle, and business domains. Skills should
compose these shared libraries rather than duplicating path, cache, identity, or
freshness logic.

1. **Runtime and Storage Foundation**
   * Configuration, provider access, model calls, scheduling, logging and
     error contracts are defined in [Infrastructure](../SKILL.md#infrastructure).
   * `lib.slugify` supplies shared slugification; domain objects choose identity
     and `lib.insights.paths` formats insight filenames.
   * `lib.storage` owns relative-path storage routing; follow
     [Datasets and storage](../SKILL.md#datasets-and-storage).

2. **Dataset Domain (`lib.datasets`)**
   * Owns dataset locations, source discovery, conversion, chunking,
     embeddings, indexing, retrieval and refresh-status markers. Follow
     [Datasets and storage](../SKILL.md#datasets-and-storage).

3. **Insight Domain (`lib.insights`)**
   * Owns insight paths, filenames, selection, freshness metadata and
     generated-dataset reconciliation. Follow
     [Insights: artifacts and freshness](../SKILL.md#insights-artifacts-and-freshness).
   * Do not use legacy `insight_filepath` or `insight_refresh` patterns.

4. **Startup Domain (`lib.startups`)**
   * Owns startup identity, standard startup dossier layout, active startup
     dataset creation, and external startup source hydration.
   * `identity.py` resolves canonical startup slugs and configured aliases.
   * `dossier.py` creates the standard startup raw and parsed subdirectories
     (`data-room`, `linkedin`, `dealum`, `snippets`, `post-deal`) and active
     markers.
   * `sources.py` exposes `ensure_startup_dataset(...)`, which verifies local
     startup data and optionally refreshes it from Dealum.
   * `startups/dealum/` owns Dealum reconciliation, exact name/application-code
     matching, application Markdown rendering, manifest hashing, document
     downloads, and import results.

5. **People Domain (`lib.people`)**
   * Owns the canonical `Person` model, person identity matching/merging,
     editable person roster parsing, and person dossier assembly.
   * Identity, matching, roster parsing and profile contracts are defined in
     [People: identity, evidence and workflows](../SKILL.md#people-identity-evidence-and-workflows).
   * `dossier.py` builds a person's document dossier and incidental mentions
     from parsed dataset content and semantic search.
   * `linkedin/` owns LinkedIn identifier parsing, dataset-local profile files,
     the outstanding-profile registry, Apify job reconciliation, manual
     imports, technical payload cleaning, and `Person` enrichment. Stored
     profiles exclude web links and low-signal provider fields before dataset
     indexing. Only generic Apify access remains in `lib.infrastructure.apify`.

6. **Checklist Audits (`lib.batch_audit`)**
   * Owns checklist parsing, concurrent assessment, canonical JSON validation
     and deterministic table rendering. See [Checklist audits](../SKILL.md#checklist-audits).
     Domain synthesis stays in the calling skill.

7. **Small Utilities**
   * `lib.ephemeral_dataset` prepares temporary generated datasets in Qdrant.
   * `lib.markdown_tables` owns shared Markdown-table parsing.
   * `lib.litellm_cleanup` and `lib.runtime_noise` support runtime cleanup/noise
     handling. JSON parsing, repair and review belong to shared AI generation.

## Skill Directory Structure

Use this layout for a new executable workflow. Operational tools and shared
utilities retain their existing entry points; instruction-only skills need
only their instructions and relevant references. Do not add facades for symmetry.

```text
{{REPO_ROOT}}/
├── lib/                        # GLOBAL: Shared infrastructure (env, logger, adapters, …)
│
├── skills/
│   └── <SKILL_NAME>/           # The individual skill package
│       ├── SKILL.md            # Mandatory: AI instructions and metadata for the skill
│       ├── __init__.py         # Makes the skill directory a Python package
│       ├── __main__.py         # Thin CLI Entry Point (Typer app)
│       ├── <skill_name>.py     # Primary Class/API facade - Logic Entry Point
│       ├── core/               # (Optional) Subroutines and heavy business logic
│       │   └── __init__.py
│       └── utils/              # (Optional) Skill-specific stateless helpers
│           └── __init__.py
│
└── tests/                      # GLOBAL: pytest suite
```

* **`SKILL.md`:** Required at the skill root, with matching `name` and a concise
  capability/trigger description. Workflow documents use Inputs and outputs,
  Workflow and dependencies, Side effects and failure behavior, Usage and
  References. Operational documents use Operations and effects, Usage and
  References. Standards retains its category structure.
* **Examples:** Document actual CLI options. Harness CLI arguments support ordinary
  shell quoting. Use `--` before the slash command when supplying skill options
  separately: `python -m skills.harness -- /command "value" --option "value"`.
  Whole-command quoting with inner double quotes remains supported.
* **Ownership:** Root AGENTS owns working procedures; standards owns shared
  contracts; skill documents own workflow differences; configuration owns domain
  prompts and criteria. Historical reviews are evidence, not new instructions.
* **Entry points and public APIs:** Follow [Skills and orchestration](../SKILL.md#skills-and-orchestration).
* **`core/` & `utils/` (Optional):** These directories should only be generated if the skill is complex enough to require them. 
  * **`core/`:** Contains internal subroutines and heavy lifting.
  * **Local `utils/`:** Contains stateless helper functions strictly unique to this specific skill. (For cross-skill shared infrastructure, use the top-level `lib/` directory instead.)
