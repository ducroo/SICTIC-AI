# Open WebUI and RAGFlow assessment

Assessment date: 5 September 2026. Baseline: the accepted [RAG backend requirements](rag-backend-requirements.md), Google Chat and existing Python skills, local files synchronized by rclone, and a production Mac mini using a cloud LLM.

This is a documentation and source-code assessment, not a deployment benchmark or security acceptance test. Release pages currently identify [Open WebUI v0.11.3](https://github.com/open-webui/open-webui/releases/tag/v0.11.3) and [RAGFlow v0.27.1](https://github.com/infiniflow/ragflow/releases/tag/v0.27.1) as the latest releases. Source references below use those tags; live documentation and the separate oikb package can evolve independently.

## Judgment

Open WebUI is the better first candidate for this particular operating model. The strongest reasons are its packaged local-folder synchronization, direct access to stored extracted document text, and deployment support for ARM64. RAGFlow offers more extensive ingestion and visual workflow controls, but introduces a larger service stack and requires more work around the local-folder and full-document contracts. Evidence for those differences appears below.

Neither application supplies the complete confidentiality policy for a Google Chat bot with access to every startup and the member collection. Nor does either replace the investment-specific ranking, expertise configuration and insight lifecycle automatically. These remain integration responsibilities. Whether either migration produces a worthwhile net reduction in code is still unverified.

## Findings that affect the decision

### Local synchronization

oikb is a separate Open WebUI ecosystem package, not rclone itself. It can track additions, modifications and deletions using content hashes. Its documentation requires Open WebUI 0.9.6 or later, so the assessed server release meets that stated prerequisite. Upload completion is distinct from completed extraction and indexing. Invoke sync after rclone completes, and verify readiness before claiming that a task uses current documents. Do not point one knowledge base at the common parent of all startups. [oikb documentation](https://docs.openwebui.com/ecosystem/knowledge-base-sync/)

For RAGFlow, the absence of a documented local-directory synchronizer in the inspected material is an evidence gap, not proof that no community package exists. Its native cloud connectors are less valuable for this design because rclone already owns cloud synchronization. [Inspected connector configuration](https://github.com/infiniflow/ragflow/blob/v0.27.1/docs/guides/data_source/data_source_configuration.md)

### Full-document access

Open WebUI's `GET /api/v1/files/{id}/data/content` returns the stored extracted content. `GET /api/v1/files/{id}/content` serves the original file. That directly supports the existing pattern of searching first and then reading a complete document. It does not prove extraction captured every table or page; that remains R8. [Pinned implementation](https://github.com/open-webui/open-webui/blob/v0.11.3/backend/open_webui/routers/files.py#L675)

RAGFlow's dataset document download and its agent-attachment download should not be confused with a guaranteed full parsed Markdown export. In particular, the attachment endpoint's `ext=markdown` is documented as a content-type hint, not a conversion instruction. Preserve canonical parsed text until an equivalent path has been demonstrated. [Pinned API contract](https://github.com/infiniflow/ragflow/blob/v0.27.1/docs/references/http_api_reference.md#download-attachment)

### Spreadsheet quality

The repository's [spreadsheet converter](../lib/infrastructure/document_conversion/docling_stack/spreadsheets.py) deliberately handles visible sheets, numeric formatting and missing cached formulas. Merely selecting Docling does not establish equivalent behavior.

In RAGFlow v0.27.1, the spreadsheet Markdown helper calls `pandas.read_excel` without selecting all sheets, which uses the first sheet. The inspected pipeline's HTML branch takes the first returned table. Other parsing modes can process multiple sheets, so this is a warning about specific modes rather than a general claim that RAGFlow supports only one sheet. These modes do not pass the all-sheets requirement as written. [Spreadsheet helper](https://github.com/infiniflow/ragflow/blob/v0.27.1/deepdoc/parser/excel_parser.py#L254), [pipeline branch](https://github.com/infiniflow/ragflow/blob/v0.27.1/rag/flow/parser/parser.py#L883)

### Confidentiality and future deal-lead access

Open WebUI provides scoped knowledge tools and access checks, but its documentation also describes discovery across everything an account can access when no knowledge base is attached. For this integration, construct the allowed scope in trusted code and use direct scoped APIs; do not let the model choose unrestricted collections. [Knowledge behavior](https://docs.openwebui.com/features/workspace/knowledge/)

The same integration rule applies to RAGFlow's dataset-scoped requests. A task may use one startup plus permitted member profiles for matching, while a multi-startup report remains operations-only. Google Chat identity, response audience and output-folder checks are application responsibilities for both candidates. Future deal-lead access must be tested separately from operations-only access.

### Deployment and licensing

Open WebUI's base application can run alone, but the realistic comparison includes a capable extractor and the chosen vector store. Its current guidance recommends PGVector for multi-worker deployments and treats Qdrant as a non-core integration. Keeping Qdrant is possible, but is not automatically the lowest-maintenance configuration. [Deployment guidance](https://docs.openwebui.com/getting-started/essentials/)

RAGFlow's standard Compose stack includes MySQL, S3-compatible object storage and a Redis-compatible service alongside its document engine. Additional features can add more services; they are not all required at once. Its documented ARM64 build requirement is conditional on the actual production Mac mini architecture, which has not been supplied. [Compose](https://github.com/infiniflow/ragflow/blob/v0.27.1/docker/docker-compose-base.yml), [platform notes](https://github.com/infiniflow/ragflow/blob/v0.27.1/README.md)

RAGFlow uses Apache 2.0. Open WebUI uses its own license with a branding-preservation condition and specified exceptions, including deployments with no more than 50 direct users in a rolling 30-day period. That is a branding condition, not a blanket 50-user limit. Account for the license when planning the later rollout; this assessment does not resolve its application to a headless Google Chat integration. [RAGFlow license](https://github.com/infiniflow/ragflow/blob/v0.27.1/LICENSE), [Open WebUI license](https://github.com/open-webui/open-webui/blob/v0.11.3/LICENSE)

## Recommendation and remaining evidence

Evaluate Open WebUI first as a narrow replacement behind existing skills, with one knowledge base per startup, separately restricted member data, and oikb after rclone. Keep the expertise configuration, investment workflows and local insight writers. Preserve the current spreadsheet conversion path until a replacement passes the extraction comparisons.

RAGFlow becomes more attractive if richer ingestion controls or a deliberate move into visual workflow authoring is valuable enough to justify the larger deployment. That is not necessary to preserve the current Google Chat experience.

Before choosing either, demonstrate confidentiality under mixed and concurrent tasks, full-document and spreadsheet fidelity, reliable refresh/deletion, production-equivalent resource usage, and a measured net code reduction. No new cost, latency, security or line-saving figure is presented as measured in this assessment.
